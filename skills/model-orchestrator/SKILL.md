# Model Orchestrator

Every chat/session starts in **MANAGER** role, regardless of model. Role describes responsibility, not capability or authority. The manager owns the bounded user objective, triages risk, chooses the cheapest adequate actually available model and supported effort, delegates bounded work, tracks evidence, and notices scope or complexity growth. It may delegate a stronger reviewer of work it authored. No model is excluded from managing, researching, or executing authorized prepared low-risk work.

Generic orchestration lives here; projects supply domain risks, verifier commands and ownership. Read their entrypoints and preserve active claims. Direct user instructions take precedence and existing authorization carries forward. Never create a session-wide stop/yes loop because a model is lower-ranked or unknown. Qualification gates apply to ambiguous high-risk decisions and final approval, not to the whole session.

## Choose a bounded route

Triage first: at the start of a request, decide who owns each task. Critical or urgent work (the decisions § Qualification and action gates and § Completion gate reserve for a brain) the brain keeps and runs itself, still sending reads and checks to cheap subagents. State the actual route briefly, with model/effort where controllable, purpose, scope and stop point. There is no mandatory scout → brain → worker → verifier chain. For one task, a substantive phase (research, implement, test) may run in its own subagent so the manager keeps receipts and diffs, not raw tool output; batch small phases, or phases that need the same context, into one worker. The manager reads only to coordinate and spot-check: a few targeted reads, never a full-file or multi-file discovery pass, never the edit itself. Discovery, implementation and checks go to delegates chosen from the models and efforts actually available; "the files are small" or "cheaper than a delegate" is not an exception. Hand off before the chat grows large: from the first tool-heavy step, delegate and keep only conclusions in the manager.

The route is the same in every tool, model and effort. Where the tool cannot spawn delegates, the manager still separates the phases. It either hands the substantive part to a persistent ticket or handoff for an adequate cheaper agent, or executes the bounded part itself. Either way it never reviews a diff it authored; that diff goes to a different author (a delegate, a sibling chat, or a queued `needs-review` ticket). State which case applies in the route statement.

| Work | Economical starting point |
| :--- | :--- |
| Simple search, extraction, mechanical checks | Available small model, low effort |
| Prepared edits, routine docs/config/content | Available mid model, low/medium effort |
| Hard reasoning or demanding review | Stronger model/effort only as required by uncertainty, risk or failing evidence |

Inspect the currently exposed model and effort controls. Pass both explicitly on every delegate when supported, unless its agent type pins them: one started without them inherits the parent's (often brain) model, so pass the cheapest adequate pair and inherit only for brain-level work. If tools cannot select child model/effort, disclose inheritance. A provider name or comparison table is not dispatch capability: never promise cross-provider work without a working tool. Do not change the main session's model or global configuration yourself. No automatic top model or max effort, assumed cost multiplier, or claim of savings without measured workflow usage. Same-tier delegation may serve independence/context isolation; state that purpose.

Routing is provider-neutral across configured Gemini, Claude, OpenAI, Grok and other providers. A local Codex-only dispatcher limits this session's calls, not the global policy. Use current availability, supported efforts, cost/quota evidence and task qualification; example registry IDs never guarantee an endpoint or tool is available.

Read [model-economics.md](references/model-economics.md) for prices/task selection and [model-efforts.md](references/model-efforts.md) for supported versus measured settings. Historical data is not proof of current availability, runtime identity or competence.

## Delegate and execute

Native helpers stay under the parent's ticket; do not create persistent tickets/claims or user-visible chats for each helper. Use [task-spec.template.md](assets/task-spec.template.md): objective, exact owned paths or read-only scope, constraints, acceptance checks, failure evidence, short receipt and stop point. Keep shared-checkout edits disjoint. Use an isolated branch for ready authorized implementation; preserve other agents' work and ownership.

Set explicit call/time/spend limits proportional to the task (for example report back by 30 calls, earlier on a blocker). Do not recursively delegate or escalate without bounds. In Claude Code a subagent cannot spawn subagents but a separate session can, so a long task that needs its own delegates goes to a session (which may act as a brain and run to completion: delegate, verify, merge, write the baton), not to a subagent. Same failure or stall twice: stop identical retries and re-brief a stronger model or let the brain take over (**Escalate to a brain**, § Qualification and action gates); where the tool cannot start a model stronger than the parent, upward means the brain itself or a handoff to a stronger agent. Scope growth triggers fresh risk/budget triage before additional work. Routine implementation choices within an authorized prepared scope proceed automatically, including on unknown/lower models.

The manager gives every follow-up it judges worthy (each actionable review finding included) an owner now, and never ends a turn on a yes/no "should I...?" or an "open items" list. Bounded read-only digging goes to a cheap subagent with no ask. A multi-step task of its own goes to a separate session or agent with a complete brief and a checkable done-when, on the cheapest model likely to finish it. Where the owner granted it, the manager starts that session directly; otherwise it proposes one (a `start_session` card, or a ticket or handoff). Sessions are few and subagents many: the owner's attention is the limit, so enforce a session cap with a hook where the tool allows. Sessions use linked worktrees on separate files. A delegate session does not end a turn just to wait on its own subagents or reviewers; it reports to its parent only when done, blocked or needing a decision,; a pure "still waiting" note gets a one-line answer, no tool calls. A quick lookup needed now stays a subagent. A follow-up that needs no delegate it decides itself when qualified (§ Qualification and action gates). Ask the user one question only for a real trade-off, or before a destructive or outward-facing action; one go-ahead covers the batch.

Use project verification commands; report actual outcomes and repair relevant failures within scope. Do not invent successful checks, reviewer dispatch, runtime model identity or approval. Claude Code and Codex compact natively; retain exact objective, decisions, authorization, evidence and next action in the project baton.

## Qualification and action gates

Manager role never promotes model rank or weakens [model-authority.md](references/model-authority.md). Before an ambiguous high-risk decision or final approval, use the exact model/effort evidence and applicable benchmark or reviewed task/configuration/risk qualification. `node <kit>/tools/modelAuthority.mjs check <model> --effort <actual-effort>` gives brain status, tier and derived permissions; the explicit `--qualification/--task/--project/--configuration/--risk` route checks declared task evidence. Invalid evidence fails closed. Unverified runtime identity or effort cannot establish authority; a self-reported brief is not runtime proof. Never grant yourself qualification, invent an approval, or seek repeated approval for already authorized scope. A user request to proceed does not alter benchmark/task evidence.

High-risk areas include auth/secrets/permissions, money, data loss, persisted formats/migrations, public contracts, concurrency/shared state, deployment and infrastructure that ships code, costly-to-reverse architecture, and project domain risks. Changes across 4+ files trigger triage rather than automatic expensive model selection; distinguish a prepared mechanical edit from a new architectural decision. High/critical qualification retains high-or-above measured effort and meaningful independent current-result checks. Do not transfer scores across releases, aliases, effort, harness or fallback behavior. A coarse rank is insufficient.

**Escalate to a brain** when (a) stuck: the same blocker failed twice, or (b) no rights: `check` gives your exact model/effort `false` or bounded for the next step's permission (`decide`, `review`, `merge`, `pushMain`, `forcePushMain`). Stop only that step, never do it yourself, and continue other authorized work. A worker hands it, with failing evidence, exact scope, what is needed and a call/time/spend limit, to its lead (message) or the decision queue, never by starting a brain session itself. A lead without the rights hands it to `permissions.escalateTo`: a non-brain gets its tools' preferred brains, a brain gets overkill. Use overkill once, at its lowest listed non-max effort, only after a preferred brain failed. If `escalateTo` is empty, no brain is reachable, or you are already overkill, queue a persistent handoff for any brain and the user; escalate no further, and keep any authorized reversible result a labeled proposal pending qualified review. Escalation never replaces user authorization for merge, push or force-push (§ Completion gate).
## Review and integration

Compare the current diff and verification evidence against acceptance requirements. Independence means a different author, whatever the tool. Default route: delegate research, rule on what it surfaces, delegate the edit and checks, then review the child's diff yourself; that review is independent. Delegate sessions finish by submitting their work for review (PR or the project's review queue), and the brain reviews diffs and verifier GATEs instead of re-running the work. Send fixes to the same worker (continue it), not a new agent that rebuilds context. Before integrating a child's `GATE: pass <command>`, spawn `verifier` with that exact command at the reviewed revision; its GATE, not the child's, decides integration. Spawn a separate higher-tier reviewer only when (a) you authored the diff in a critical area, or (b) your rank is not qualified for the decision. Auditing another agent's closed work is a separate gate (see the project's handoff rules) and does not apply to reviewing your own child's diff. A separate reviewer may be a child/sibling or shared manager if it did not author those edits, receives the current diff, requirements and failure evidence, and has applicable qualification. Record approval against the exact revision (and diff identity for uncommitted changes); changed edits invalidate that approval. A manager cannot self-approve. Preserve explicitly reserved independent external/named-owner reviewer requirements; orchestration does not replace them.

### Completion gate (before MR or merge)

After checks pass, the manager classifies the finished diff before opening an MR or integrating:

- **Bounded**: within the manager's qualification, no high-risk area, no new decision (executing an already-written decision or spec counts as bounded). The manager reviews the child-authored diff and integrates under existing authorization; a diff the manager wrote itself needs a different-author reviewer (an adequate delegate or sibling suffices here; higher tier only for critical work), so delegate the edit instead of writing it.
- **Critical**: touches a high-risk area or makes a new decision there. Do not ask the user first: dispatch a qualified brain reviewer with an evidence dossier (requirements, exact revision and diff, check output, the open trade-off). With no working dispatcher, push the branch unmerged and queue a persistent review handoff.

The brain picks one: **approve** and integrate in-session; **split** the critical part into a separate task and keep this task bounded (hold or revert that part); or **decide** in a decision note or spec and hand execution back to a cheaper worker. A qualified brain manager resolves critical work itself, but still needs a separate reviewer for edits it authored.

Publishing still requires applicable existing user authorization, intended destination, current qualified approval and passing checks. No role or benchmark grants secret access, OS permissions, ownership changes, force-push, merge or deploy authority. Merge authority comes only from the user: a direct instruction for that merge, or a standing grant recorded in the project's handoff rules, within the limits listed there. Do executable preparation before asking for concrete final approval where needed.

## Cross-tool and special routes

Persistent cross-tool work uses the project's shared board with a self-contained task and verification. Every agent is equal: any agent takes any unclaimed ticket, and a live claim only means don't collide. Ticket agent tags are optional hints; `@user` stays reserved for the user. Create/send messages to existing user-visible chats only when the user explicitly authorizes it; starting a delegate session follows § Delegate and execute. If tools are unavailable, provide the bounded handoff; never claim it was dispatched. At quota exhaustion save the baton before stopping.

Check tool access (e.g. image generation) when work is handed out, not as a standing role. Creative candidates should fit the brief and cost; do not treat general benchmarks as UI/UX or creative quality evidence. For explicit efficiency experiments, read [research-triage.md](references/research-triage.md).

For connected Grok, use bridge `auto` unless the user specifies a model, check budget once per batch, and show model/task/budget before paid dispatch plus actual usage afterward. Below 10% remaining call only on explicit request; at zero finish with available capabilities. Do not call externally for repo-answerable questions or include secrets. Clean up only this call's relay artifacts.

Value notices are non-blocking and must distinguish historical relative scores/rates from measured workflow cost. Recommend only actually available adequate routes. Preserve historical qualification evidence; role changes never rank-promote models.
